# 读并发到 6 条就到顶了；而那个"掉到 2.8"是宿主机侧的临时窗口（2026-09-20）

## 结论

三件事，一条推翻了我自己同一天早先的判断。

**一、加并发没用，6 条就已经到顶。** 用 2026-09-16 那份记录留下的同一个探针
（`/srv/localmoe/targets/io-ceiling/disk_ceiling`）、同一份真实路由形状，冷缓存下扫了
`1 / 6 / 8 / 12 / 16 / 24 / 32` 条线程。**在快、慢两个窗口里各扫一遍，结论一样**：

| 线程 | 1 | 6 | 8 | 12 | 16 | 24 | 32 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 慢窗口（当天早些） | `1.028` | `2.756` | `2.693` | `2.768` | `2.779` | `2.740` | `2.753` |
| 快窗口（核实后） | `1.047` | `3.557` | `3.454` | `3.653` | `3.550` | `3.501` | `3.669` |

两行都是**6 之后全平**。所以"再加几条流"这条路是死的，不用再试。相对 1 条，6 条约
`3.4x`（快窗口），之后再无增益。

**二、`3.79 GB/s` 是真的，能复现；我早先写的"它是被页缓存抬高的"是错的。**
我在同一份记录里断言过旧记录那个数偏高，依据是"旧记录用的是 8 token 的 plan，有 2.21x
重复区域"。**这个依据站不住**：我查了原始的驱动脚本 `.zcode/io-ceiling/run_matrix.sh`，
它跑 `expert-6t-reuse-buffered` 用的是 `plan-expert.tsv`，而那份 plan 的重复因子是
**`1.000x`**（`1548` 行、`3.45 GB`、无重复区域），与我自己建的 `plan-one-token.tsv`
形状完全相同。用原样的命令重跑：

```
快窗口内 20 次冷跑：min 3.517  max 3.748  mean 3.658  stdev 0.067
5 次复核：          3.543  3.556  3.604  3.734  3.698
```

与旧记录的三跑（`3.5907 / 3.6514 / 3.7840`）一致。**`3.79` 没问题，是我错了。**

**三、"掉到 2.8"是一段临时窗口，不是永久退化，而且最可能是宿主机侧的盘竞争。**
同一二进制、同一 plan、同一命令，当天早些给 `2.69–2.80`，晚些给 `3.54–3.75`，差约 `25%`。
我逐个排除了能在客户机里查到的解释：

| 假设 | 怎么测的 | 结果 |
| --- | --- | --- |
| plan 形状不同 | 对比三份 plan 的重复因子 | 都是 `1.000x`，**排除** |
| 客户机内存压力 | 填满 12 GB 页缓存再 `drop_caches` 后读 | `3.73 / 3.70 / `3.62`，**不成立** |
| `read_ahead` 太小 | 调到 1 MiB 重测 | `3.6196`，**无变化** |
| `O_DIRECT` 差异 | `direct=0/1` 各跑 | 无收益（`2.73` 对 `2.59`），**排除** |
| 客户机自身有进程抢盘 | `ps`、`kworker` 计数、`diskstats` | 干净，**排除** |

而**同一个盘上只要多一个读者，速率立刻掉到那个慢档**：加一条独立 `dd` 读别的分片时，
探针从 `3.6196` 掉到 **`2.4584`（−32%）**。**这正好是那个窗口的幅度**。客户机看不见
宿主机（Windows）对同一块物理设备的 I/O，所以这一类竞争只能表现为"莫名变慢"。

另有一条独立旁证：`/proc/sys/kernel/random/boot_id` 在我两次调用之间就变了，`uptime` 反复
是"up 2 min"，`dmesg` 里 sdd 反复 mount/unmount——**WSL 虚拟机在会话之间反复重启**，
每次都要重新建立宿主机侧对 VHDX 的缓存视图。宿主机本身没重启（Windows 上次开机
2026-09-16 12:13）。这也属于客户机之外的因素。

**关于"页缓存复用"的更正。** 我早先由"8 token plan 有 `2.21x` 跨 token 重复区域"推出
"稳态读大量命中页缓存、所以盘不是瓶颈"。这条**站不住**：`2.21x` 那段重复只存在于我用来
探针的那份 8-token plan 里，**引擎实际不是那样读的**——我把 plan 的属性和引擎的行为混为
一谈了。

引擎自己的账指向"真的走盘"：`routed` 每层读 `80.22 MB`，`read_ns` 六个 lane 合计
`122.61 ms`、`routed` 墙 `18.05 ms`。按每 lane 摊（`13.37 MB / 20.4 ms`）聚合约
`3.9 GB/s`，按墙算约 `4.4 GB/s`——**贴着冷盘的 `3.66`，离 warm 的 `10–40` 差一个数量级**。
所以可稳妥说的是：**稳态读体量上确实是真实盘读，不是缓存命中**。但 `3.9–4.4` 略高于冷盘
实测，那一点差可能是 lane 之间部分重叠、也可能是少量命中，**本次没拆，别把它当精确值**。

## 对"地板"的意义

修正后重算（冷盘取快窗口的 `3.66 GB/s`）：

- **读侧**：稳态 routed `3.45 GB` 走冷盘 = `0.94 s`。
- **非读侧**：shared MLP `0.16` + attention `0.56` + router `0.11` + 专家 kernel `0.47` +
  final head `0.11` ≈ `1.41 s`。

两侧取大值 → **地板约 `1.3–1.4 s/token`，由非读侧顶着**。这与 `现状.md` 的 `1.6–1.8 s`
方向一致（那份也认为接近地板），只是原因归到算力/同步侧而不是盘。

但**这个地板估计带一个我没解决的不确定性**：读侧速率在 `3.66`（快窗口）和 `2.75`
（慢窗口）之间晃 `25%`，非读侧的 `1.41 s` 里也含主机同步步。所以 `1.3–1.4 s` 是量级，
不是精确值。

## 这次没有声称的部分

- **没有改引擎**。全部是独立回放的量测，没有产生新的引擎结果文件，所以**没有新的钉死值**。
  引用的引擎数字（`read_ns 122.61 ms/层`、`wall 18.05 ms/层`）都是从既有
  `/srv/localmoe/targets/residentfill/r{1..4}-resident.jsonl` 里读出来的。
- **慢窗口的根因没有直接证据**。我证明了"同一盘上多一个读者会掉 `32%`"，幅度吻合，
  但**没有抓到宿主机侧那一刻在做什么**（`typeperf` 要求管理员权限，没跑成；
  Windows 侧页面缓存与 Defender 之类都不可见）。所以这是**最合理的解释，不是已证事实**。
- **没有试 mmap、没有试更大单次读长、没有碰 WSL2 的 VHDX 配置**。不在本次提问范围。
- **`2.21x` 那份 8-token plan 从哪来没查**。它可能是早期某次为别的目的生成
  （把 8 个 token 的轨迹串在一起），我没有回溯它的生成脚本。
- **"页缓存复用"没有再往下做**。既然引擎实测≈冷盘，那条线索的优先级下调了；
  但它并没有被证伪到"绝无可能"的程度——长 run 里工作集 `12.46 GB` 仍小于 15 GiB 内存。

## 复现命令

```bash

for t in 1 6 8 12 16 24 32; do
  sync; echo 3 > /proc/sys/vm/drop_caches; sleep 1
  "$BIN" "$PLAN" reuse 0 "$t"
done
```

## 未决事项

1. **抓宿主机那一刻在做什么**。需要管理员权限的 Windows 侧计数器
   （`typeperf` / 资源监视器 / `Get-Counter`），或者把模型盘换到独立的物理设备上做对照。
   在这之前，"慢窗口 = 宿主机盘竞争"只是最合理解释。
2. **给性能跑加一个"盘速率现场闸门"**：正式 A/B 之前先跑一次这个探针，若落在 `2.7`
   档就直接判定"环境不合格、本批作废"。这比事后怀疑数字可靠。
   本机两三个星期一次硬件断电，加上 WSL 反复重启，环境噪声必须当场拦。
3. **读侧到底能不能改善**：既然引擎实测≈冷盘 `3.66`，而 warm 能到 `10+`，值得再确认一次
   长 run 下工作集是否真的留在缓存里（本次的推断被推翻了，要重做）。
