# 每层只建一个专家槽位：8 步 103.38 s → 70.06 s（2026-09-16）

## 结论

`ExpertSlot` 的 pinned 主机缓冲改成**每层建一次、6 个专家轮流重填**，数值一字未变，
**8 个 token 从 `103.38 s` 降到 `70.06 s`（−32%），稳态每个 token 从 `12.5 s` 降到 `8.28 s`（−34%）**。

正确性用三条独立证据钉住：

- 1 步四个钉死值全对：`argmax=55222`、`hidden_bf16_digest=5ed8bf88beae3cfe`、43 层、峰值 `1466499072`
- **8 个 token 的 `hidden_bf16_digest` 逐个相同**（`5ed8bf88beae3cfe`、`316e5495ca424b39`、
  `a521547b2586e458`、`1963dfeaaf30264c`、`b970da7913a57a1c`、`12c6b45cecf9d53b`、
  `e0f441542fa53991`、`69ed859929ee9042`）
- 峰值显存同为 `1466499072` 字节

这一轮还顺手回答了上一份记录里挂着的那个问题：**贵的是页锁定，不是拷贝。** 重填这条路保留了
memcpy 却把每专家的开销从 `14.40 ms` 降到约 `2.4 ms`，所以 13.4 MB 的拷贝只要约 `1.2 ms`
（约 11 GB/s），剩下的是 `cuMemHostAlloc` 锁页。

**没声称的部分**：改动**没有**合并到交付分支，只在 `exp/slot-reuse` 上（`c3c1be8`）；
只改了预取那条路（`COLIBRI_V4_FLASH_PREFETCH=1`），非预取那条路仍然是每个专家重建；
形状不匹配时的回退分支**没有被任何一次运行走到过**（V4-Flash 的专家形状恒定）；
serve 路径和长 prompt 仍然没测。

### 两个数字位移的解释与未解释

- **`shared` 降 23.5 ms/层，和预取线程自己记账的那两项（`read` + `alloc`）降 23 ms 对得上。**
  `shared_ns` 的墙 = max(shared 计算, 预取线程读盘) + join（见基线记录第 3 条更正），
  所以预取线程快了多少，`shared` 就降多少——**预取线程被主线程的锁页/解锁页churn拖慢了**，
  这一点从两边数字一致看得出来（机制是推断，数字吻合）。
- **`fixed` 反而涨了 22 ms/层，这个没解释。** 它自己的两项都没变（`fix.rdalloc` 151.2 → 148.7、
  `fix.h2d` 23.2 → 23.0），但墙从 43.2 涨到 65.2。一个说得通的猜测：每层的总时间从 290 ms
  降到 193 ms，而固定参数的预取每层仍然要 148 ms，**留给它藏身的余地变少了**，
  本来被盖住的部分露了出来。要证实得单独看固定参数预取线程的到达时间，这次没测。

## 代码变更

`exp/slot-reuse`（`c3c1be8`），只碰两个文件（`+93 −1` 行）：

- `expert_slot.rs`：新增 `new_or_restage(recycled, …)`（形状匹配就重填、否则退回 `new`）、
  `staging_shapes_match`、`restage_weights`（把 6 份权重拷进已有 pinned 缓冲并重新 H2D，
  更新 `weight_h2d_ms`）。`new` 一个字没改。
- `layer_rows.rs`：预取那条专家循环里加一个 `recycled_slot`，循环尾把槽位放回去。

**为什么这样改**：QD4 那条路早就在用同一套办法——`load_range_execute_into` 就是
"往已有 pinned 缓冲里重填再上传"，从不按专家重建槽位。这次只是把预取那条路对齐到同一个做法。

设备缓冲和 event 也顺带被复用了（同一个槽位对象活着），但它们本来就便宜（合计 0.3 ms），
不是这次的目的。

**回退是显式的**：`staging_shapes_match` 只要有一块对不上就整个退回新建，所以不同几何的专家
不可能被塞进同一个槽位。代价是这条路没被运行覆盖过（V4-Flash 形状恒定，走不到）。

## 未决事项

1. **要不要合并到交付分支。** 数值零变化、有 8 个 digest 和钉死值做证，按"交付分支只收
   验证过的东西"是可以进的；但基线数字会因此作废（`103.38 s` / `12.5 s` 要改成
   `70.06 s` / `8.28 s`），所以这是一次需要显式决定的合并，不是顺手提交。
   > **2026-09-16 深夜：已合并**，合并提交 `67e80c3`。合并后交付分支的 rust 代码与 `exp/slot-reuse`
   > 逐字相同（`git diff` 只剩文档），重建 59 条警告、单步四个钉死值复现，
   > 8 步实跑 `/srv/localmoe/targets/delivery-merged-8step.jsonl` 的 8 个 digest 逐个相同。
   > **当次墙 `77.72 s`，别把它和 `70.06 s` 当矛盾**：同一份代码当天的墙在 `76.09`–`81.34 s`
   > 之间都出现过（盘状态不同），`70.06 s` 是下午那次的条件。交付分支的基线自本次合并起
   > 是本记录的数；`2026-09-16-sm120-nonresident-baseline.md` 里那份 `103.38 s` / `12.5 s`
   > 只描述合并前的历史。
2. **`fixed` 那 +22 ms/层 需要单独查**：固定参数预取线程每层仍要 148 ms，而层时间只剩 193 ms，
   隐藏余地不多了。这很可能是下一个瓶颈的形状——**继续优化别的地方，它会继续涨**。
3. **非预取那条路（`PREFETCH=0`）仍按专家重建槽位**。基线不用它，所以这次没动；要用它的时候
   得同样改一遍，或者干脆收敛到同一个槽位池。
4. **`shared` 那 45.4 ms/层 仍然没有内部计时**（基线记录未决事项 2 的延续）。现在它是第二大项，
   `LayerStageTelemetry` 里还是只有 `shared_ns` 一个字段。
5. **attention 的 `compressor` 16.0 ms/层 + `indexer` 5.1 ms/层**（基线记录未决事项 3），没动。
   现在 attention（31.2 ms/层）已经和 routed（47.5）同一个量级了。
6. **serve 路径与长 prompt 仍未测**：预填充那件事（真实 prompt 每个 token 约 17 s）不受这次改动影响，
   它仍是"这条路能不能用"的门槛。
