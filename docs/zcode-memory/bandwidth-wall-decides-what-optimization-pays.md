2026-10-03 用户提出三条判断让我核对：①27B 在 16 GB 卡上「首先得量化，还得 GPU/CPU 分层」；
②「优化算子，实际效果可能没有小模型整体存显存那么明显」；③「分页 KV + 连续批处理，在 27B 上
其实也不算一种很合格的处理方式」。核对结论：**①② 对（②的根因要改），③ 技术没错、错的是场景。**

## 核心判据：贴在哪面墙（roofline）

- 算术：**每 token 必须读的字节 ÷ 带宽 = 每 token 时间下限**。
- **贴在墙上时，优化算力完全看不见**——时间压根没花在算上。
- **决定「优化能不能看见」的是"有没有离开墙"，不是模型大小。** 用户以为是"小模型"，更准确的
  根因是：模型整块进显存 + 批量摊薄权重读取 ⇒ 才离开墙。
- 反证：拿 0.6B 跑 batch=1，它一样贴墙，算子优化一样看不见。

## 数字（规格 + 实测）

- RTX 5060 Ti 16 GB 显存带宽 ≈ **448 GB/s**（GDDR7）。[[wsl-run-environment]]
- Qwen3.8-27B @ IQ3_XXS ≈ 11.9 GB → 11.9/448 ≈ **26.6 ms/token ≈ 38 tok/s 上限**；
  实测 48–50 tok/s，靠 MTP 一趟出多 token 才越过这条线 ⇒ **基本贴墙**。
- Qwen3-0.6B bf16 1.19 GB → batch=1 地板 2.66 ms；实测 **batch 32 + CUDA graph
  6.9 ms/step 出 32 个 token = 0.216 ms/token，比 batch=1 地板低十倍以上**
  （权重一批只读一遍）。出处 [[nano-vllm-lab-wsl]]。
- 同一套物理再往外一层就是 localMoE：3.45 GB/token 从**磁盘**读、盘速 3.5 GB/s ≈ 1 s/token。
  所以那边「优化算子没用」的力度比 27B 更狠。[[flash-0731-bottleneck-map]] [[disk-speed-two-tier]]

## 三条判断的裁定

1. **量化必须、分层不必须。** 27B dense：bf16 54 GB / Q8 ≈27 GB / Q4 16–18 GB 都塞不下 16 GB，
   **Q4 这一档就必须分层 offload**；但压到 3-bit（IQ3_XXS ≈11 GB）可**全层放 GPU**
   （第三方实测 94K 上下文、~48–50 tok/s）。即：**躲开分层的唯一办法是压到 3-bit，代价是模型质量。**
2. **对，但根因是墙不是尺寸**（见上）。
3. **技术没错，错的是场景。** 两项技术各有一个前提，单用户本地 27B 两个都没有：
   - 连续批处理要「多个请求拼一批摊薄权重读取」→ 单用户并发 1，batch 恒为 1，**价值归零**。
   - 分页 KV 要「多序列抢一个有限 KV 池 + 共享前缀」→ 单序列下块表与引用计数是**摆设**。
   - **唯一例外：多轮对话的 prefix caching 仍有用**（系统提示 + 历史是同一段前缀，第二轮起可复用）。
   - 那个场景真正吃钱的是：**量化 kernel、offload 预取重叠、投机解码(MTP)、KV cache 量化**
     —— 即 llama.cpp 那条线，也正是 localMoE 已在练的手艺。

## 查表：场景 → 墙 → 该优化什么

| 场景 | 贴在哪面墙 | 优化什么才有用 |
| --- | --- | --- |
| Qwen3.8-27B @ 3-bit，单用户 | 显存带宽 | 量化、offload 重叠、投机解码 |
| localMoE（V4-Flash） | 磁盘 + PCIe | 权重分页、锁页、预取（已在做） |
| 0.6B 全量常驻 + 多请求 | 内核启动开销 / 每步固定成本 | 调度、连续批处理、CUDA graph、算子 |

**Why:** 用户会拿「模型多大」「这技术高不高级」来判断值不值得学，但真正的判据是瓶颈在哪。
把判据和数字记下来，以后「优化 X 有用吗」「某技术适不适合」这类问题可以直接查表。
**用户对 localMoE 里「优化算子没用」的直觉是对的，但结论不是"算子优化没用"，而是"它被用在了错误的墙上"。**

**How to apply:** 被问「X 优化有用吗」时先问「现在贴在哪面墙」，再查上面这张表。
讲给用户时走 [[plain-language-reporting]] 的类比法：带宽墙 = 传送带速度上限；贴墙 = 整条线的
速度由传送带决定，改分拣策略看不出效果。[[ai-infra-learning-direction]] [[nano-vllm-lab-wsl]]

## 用词更正：「搬字节的噪声」是我造的词，用户听不懂

2026-10-03 用户专门来问「什么叫做搬运噪声」。我当时的原话是「搬运噪声盖住了调度器的信号」。
**这不是正式说法，以后别再用。** 准确的表述是：一个**数值上大得多、又和你要研究的问题无关的
主导项**把真正的信号压住了——不是随机误差，是「被搬运耗时淹没」。拆成三个词讲用户就懂了：
①「搬字节」= 把权重从磁盘搬到内存再搬到显存这件事本身；②「账」= 性能报告里各项的时间占比；
③「盖住信号」= 你想观察的那个变化测不出来。这段（含上面那组数字和传送带比方）已落
`学习路线.md` 第一节的框里。[[docs-plain-register]] [[ai-infra-layer-map]]
