同一个二进制交错跑 3 轮）服务稳态 **`3.94 s/字`**（`3.631/4.085/4.117`、首字 `23.9–24.1 s`）、
命令行 **`4.04 s/token`**（`3.907/4.212/4.010`）。**差 `+0.10 s`，在两臂各自的跑间离散
（`0.49` / `0.31 s`）之内，分不出来。** 服务产出的 8 个 token 与上次逐字符相同
（`58572,42549,42549,109865,…`），所以中间落地的固定层槽位与压缩器池也没动服务面的数值。
批脚本 `rust/colibri-cuda/tools/serve_vs_cli.sh` + `serve_vs_cli_sum.py`。

**所以那个 `4.81 s/字` 只是提交旧了，不是两条路不一样。** 它是 `4cda82b` 的读数，
之后落的两个改动在命令行上合计预期 `-0.83`，服务面实测 `4.815 → 3.944 = -0.87`。
**在同一个提交上服务本来就不比命令行慢**（`4cda82b` 时命令行稳态约 `5.0`，服务 `4.81`）。
以后见到两面数字不一样，**先查两个数字是不是同一个提交、同一批**，再怀疑结构。

**2026-10-01 重验（交付线 `93423d8`，同 prompt 对照）**：这次把两面放在**同一个 prompt**上比
——服务端「你好，你是谁？」正好切成 `58572,42549,42549,109865,42549`，就是命令行那组真 5-token。

**稳态两面在噪声内相同**（差 `0.063 s`，服务自己的跑间离散就有 `0.106`）——老的「一样快」
结论在新的、低得多的绝对水平上依然成立。服务三轮的 id 串**逐字符相同**
（`58572,42549,42549,109865,42549,42549,42549,42549`），数值闸门通过。
（比 09-17 那次 `3.94 vs 4.04` 低一半多，是三个改动 + 常驻 + fan-out 默认开之后的结果。）

**首字拆解（这一步以前只拆到"首个 token 一次性建常驻库"就停了）**。服务面首字 `16.3–17.1 s`
（43 层墙 + final head），它的五个互不重叠相位是：

| 相位 | 服务首字 | 服务稳态 | 差 |
| --- | --- | --- | --- |
| `routed` | `4.6–6.1 s` | `0.32` | **+4.3~5.8** |
| `attention` | `4.6–4.8 s` | `0.56` | **+4.1~4.2** |
| `shared` | `3.4–4.0 s` | `0.58` | **+2.9~3.4** |
| `fixed` | `1.5–2.3 s` | `0.00` | +1.5~2.3 |
| `router` | `0.9–1.2 s` | `0.12` | +0.8~1.1 |

**结论：首字贵不是某一处，是每个相位一起冷**。常驻库那一下（`fixed`）只占 `1.5–2.3 s`，
即首字的 `10–13%`——「首字慢是因为建常驻库」这个说法**只解释了一成多**；大头是 `routed`（读专家盘）
和 `attention`/`shared` 各自的冷启动。所以优化 TTFT 不是一件事。
记账闭合：`首字 + 7 × 稳态 ≈ 请求墙`（服务 `17.15 + 12.34 = 29.5` 对 `30.06`；命令行 `15.58 + 12.78 = 28.4` 对 `28.36`）。

`/srv/localmoe/targets/servevscli-2026-10-01/`（同 prompt 的命令行）、

**2026-09-20 更新**：服务面**现在有**默认关的逐相位落盘口了（`fd4a864`，
`COLIBRI_V4_FLASH_SERVE_PHASE_JSONL`），见 [[flash-0731-serve-phase-sink]]。以前不写的原因
不是引擎没有数据（服务跑的就是同一个 b2 循环、逐层相位一直在收集），是网关

的拆分仍然没做**——那才是下一件事。

以下为预取门卫那次，保留作历史。

2026-09-17 查清、当天修掉并按服务重验。**服务路径曾经比命令行慢一倍，原因是固定参数的后台预取线程的门卫只认 `COLIBRI_V4_FLASH_BASE`**（`b2_runtime.rs` 的 `flash_b1_prefetch_enabled`），而服务走 `COLIBRI_V4_FLASH_SERVE`，于是每层固定参数的"读盘 + 解码 + 申请缓冲 + H2D"整套串在关键路径上。仓库里"serve 每迭代比 CLI 贵 1.75 倍、没解释"挂了很久，就是这个。

**修法已落地（`4cda82b`，交付分支 HEAD）**：门卫改成 `base || serve` 放行，并且 `COLIBRI_V4_FLASH_PREFETCH` 在这两个交付面上**默认开**（`=0` 回到串行加载）。第二半是必须的——`c/openai_server.py` 从不设 `PREFETCH`，只放宽外门的话交付服务路径仍然是慢的那一档。

重验结果（同一二进制、同一批；证据在 WSL `/srv/localmoe/targets/prefetch-gate-{serve,cli}/`）：

| | 首字 | 每个字 |
| --- | --- | --- |
| 现在的默认（预取开） | `30.4 s` | `4.81 s` |
| `PREFETCH=0` | `86.1 s` | `10.44 s` |

token id 两边相同（`58572,42549,42549,109865,...`）。命令行那条 8 步：默认 `47.0 s` 对 `PREFETCH=0` 的 `98.67 s`；8 个 digest、8 条 43 层摘要链、8 个 argmax 与 `defaults-pc-8step` 逐项 `IDENTICAL`。**唯一差异是显存峰值**：默认 `1500053504`，关掉 `1466499072`，差 `33.6 MB`。**这 33.6 MB 的机制没查**——怀疑和 `layer_rows.rs:958` 那条 `flash_routed_prefetch = 预取开 && expert_slots.is_none()` 的两条分支有关（一条线程并行读盘、一条走 routed 槽位），但那只是怀疑，别当结论引用；移植固定层槽位之前必须先把这块看清楚。

**prompt 长度不影响服务的每个字速度**：8 个 prompt token → `4.52 s/字`；91 个 → `4.44 s/字`（噪声）。**首字**才跟着长度线性涨，每多一个 prompt token 约 `2.6 s`。结构上说得通：`prompt + 生成 ≤ 128`，128 行的裸 KV 环从不绕回。

## ⚠ 那个 `4.81 s/字` 已经过期（2026-09-17 晚）

它是 **`4cda82b`** 那一刻的数（证据 `/srv/localmoe/targets/prefetch-gate-serve/`，
请求形状 `SUBMIT 1 0 54 8`，`stats` 行 `30401.883 / 4814.630`）。**它后面落了两个改动**：
`7cdd0b1`（固定层槽位，fixed 1.02→0.73）和 `9efd662`（压缩器池，attention 1.34→0.79）——
两个都不是服务专属，门卫全是 `base || serve`，所以服务同样吃。**服务今天的数应该在 `4.0` 上下。**

**而且当时服务并不比命令行慢**：同一天 CLI 那条 8 步是 `47.0 s`，扣掉冷启动那颗 token ≈ `5.0 s/token`，
服务 `4.81`——基本相等。所以"服务 4.81 vs CLI 3.70"不是一个结构差异，是**服务那个数字停在旧提交、
CLI 的数字一直在更新**造成的。两边跑的是同一条解码路径（`b2_runtime` 那条），每 token 没有理由不同；
结构性差异只有 prompt 更长只影响首字。

**没人能确认，因为服务不写 `phase_profile`。** 这是当前最值钱的一件事：
它是唯一"改了没法验证收益"的交付面，见 [[flash-0731-per-token-floor]]。

**一条通用的踩坑**：交付面有三个（`FLASH_BASE` / `FLASH_SERVE` / `FLASH_DSPARK`），实验开关的门卫经常只认其中一个。写或读这类开关之前先看门卫认哪个面；该在两条路上生效的就写成 `base || serve`。

服务每字的历史账：`16.7 s`（最开始）→ `9.87 s`（常驻 + chunk 默认开）→ **`4.81 s`（预取门卫修好，现在）**，约 0.21 tok/s。相关：[[flash-0731-baseline-run-recipe]]、[[resident-on-is-the-comparison-baseline]]、[[flash-0731-routed-read-ceiling]]、[[flash-0731-per-token-floor]]
